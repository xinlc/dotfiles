## 注释规范（强制）

> 适用于 Java / JS / TS / Vue / 小程序 / SQL / 配置。此规范为硬性交付门槛，未满足不得声明任务完成。模糊词（"尽可能""适当""完善"）不作为豁免理由。

### 何时必须写注释

满足以下任一条件即必须补注释，不得省略：

1. 新增 public/protected 方法、导出函数、组件 props。
2. 逻辑涉及：状态流转、并发/异步、缓存失效、重试/超时、权限校验、金额或时间计算、外部 IO。
3. 分支嵌套超过 2 层，或单方法超过 30 行。
4. 存在非显而易见的不变量、前置条件、副作用、失败回滚路径。
5. 修复 bug 时，注释必须说明根因，不得只描述改动。

### 注释必须包含什么（写"为什么"，不写"是什么"）

- 意图：这段代码为什么存在、解决什么问题。
- 不变量：调用前后哪些状态必须成立。
- 边界：参数取值范围、空值/越界如何处理。
- 副作用：是否改外部状态、发请求、写库、触发事件。
- 失败路径：异常是否吞掉、失败后状态如何。

禁止复述代码字面意思（如 `// i++`），禁止营销式描述（如"优雅地处理"）。

### 各语言格式要求

- **Java**：public 方法一律 Javadoc，含 @param @return @throws；复杂类补类级 Javadoc 说明职责与线程安全性。遵循《阿里巴巴 Java 开发手册》。
- **JS/TS/Vue**：导出函数与组件 props 用 JSDoc；computed、复杂 watch 上方写意图注释。
- **小程序**：onLoad/onShow 等生命周期钩子注释说明进入时的数据依赖。
- **配置/SQL**：非显而易见的配置项、复杂关联 SQL 必须行内注释说明原因。

### 反例（不得出现）

- `// 设置用户名` 紧跟 `user.name = name`。
- `// TODO 后面优化` 无 issue 链接或负责人。
- Javadoc 只有 `@param 名字` 没有说明。
- 复杂方法只有一句话注释。

### 自检门槛

交付前自问：六个月后的维护者不看上下文，能仅凭这段注释理解意图、风险、失败处理吗？答不能 → 补。public API 缺 Javadoc 视为任务未完成。
